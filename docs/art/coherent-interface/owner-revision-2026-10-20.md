## Map selection and orders

**Owner-requested:** a star selects its system and permitted body facts; the annular fleet marker selects the first fleet in stable visible roster order. The explicit roster switches between distinct Expedition and Border patrol fleets at Sol. System selection and the command-fleet identity remain separate. Hover, focus and selection have separate visible treatments; keyboard Enter selects and Shift+F10 prepares a context action.

Right-clicking a known star with an own fleet selected opens an unsent navigation preview for that fleet. A current permitted enemy contact opens a **proposed** pursuit preview. Both retain an explicit review/cancel step. The final enabled confirmation keeps a local prototype choice only; Submit to game is unavailable. This is not evidence of live pursuit integration. Following means strategic movement under legal knowledge and routes, not teleportation, guaranteed interception or hidden tracking. Stale and last-known fixtures cannot create a pursuit draft; lost and unknown fixtures disclose no current marker. Unknown shows no contact identity. Blank/uncharted right-clicks return an unavailable explanation and retain accepted intent.

The owner **endorsed the existing layout and irregular region breakup as a first visual direction**. The revised overview keeps that field but shows a sparse set of markers and labels, with secondary labels appearing at closer zoom. Zoom, pan and Fit remain presentation controls. Exact spacing is **proposed visual composition**: no new physical distance, travel cost, fixed stars-per-region or empty-region gameplay rule is inferred. Existing seeded geometry remains an illustrative fixture, not the game's generator.

## Empire and world ledger

**Owner-requested:** own-world/all-known scope; faction/control and resource-state filters; expandable system groups containing their actual named planet rows; selected-world identity retained through filtering. Uncolonised, neutral and unknown owner are separate states. Different planetary governments can appear in one system group; a system header does not assign a single owner.

Research points, credits generated, Industry and Dilithium produced are per-turn flows. Dilithium/Food stocks are separate columns. Food output, power supply/demand and logistics capacity are available through the grouped column chooser. Current active construction, project type, queue state, completed work, remaining-turn estimate availability and queue count have separate fields. Earth has an illustrative paid Cruiser at 8/16 Industry; Mars is idle. Foreign construction stays unknown; an uncolonised body does not gain a colony queue. Own inspection opens that world's exact queue; foreign inspection has no owned-world actions. No unsupported facility-production capability or ETA calculation is invented.

Blocked/paused work must retain its own supplied state/reason and progress, rather than being relabelled Idle; this fixture does not invent a pause command or a missing backend reason/estimate.

All data headers sort and have field-appropriate filters. Numeric values use numeric comparisons, with stable identity ties and unknown values separate from zero. Action cells remain controls. System groups are ordered by their first sorted matching world, with the same comparator inside the group; filtering retains only matching known bodies. Horizontal table scrolling carries the full density without reducing primary metrics to tiny text.

Totals explicitly cover the filtered OWN or KNOWN scope and give the number of current-known contributing rows. Stale foreign numeric examples are not counted as current totals. Missing facts never become zero or hidden foreign totals. Known unexploited deposits appear separately from extraction and stocks; the example asserts presence, not an exploitable quantity. Unknown survey state remains explicit.

The actual current scenario defines **Dilithium**, and infrastructure fields for Food, Industry, Research, Power and Logistics: [scenario definitions](../../../scenarios/singleplayer-demo-v1/scenario.json), [infrastructure/resource DTOs](../../../src/HobbyDS9.Contracts/PopulationDtos.cs). Those names/units inform the columns; all displayed observations and output numbers are authored fixtures, not computed simulation results. Exploration, diplomacy and espionage are desired knowledge sources illustrated with source/as-of metadata, **not claims those complete infrastructures or a safe foreign ledger projection are implemented**. A receiving adapter needs actor-filtered facts and independent availability flags before any native binding.

## Fleet roster

**Owner-requested:** expandable named fleet rows with member ships directly underneath; separate colocated fleet identities and orders; location sorting, numeric count/current/maximum-hull/damage sorting and useful search/location/hull-status filters. Hull damage means missing hull divided by maximum hull; it is not a shield or ammunition deficit. Power rating is **unavailable** because no authoritative strength metric/formula was identified or approved. It is not filled with invented combat balance.

Ship and fleet selection remain keyed by identity through sort, collapse and filters. A hidden selected fleet gets an explicit warning rather than silently selecting a new fleet. Expansion has keyboard-accessible buttons and explicit member counts; no hard gameplay fleet cap is implied. Own ship details preserve current/maximum hull, four shield pools and torpedoes. List sorting never transfers members or changes an order.

## LCARS Science editor

**Owner-requested:** substantial coloured segmented bars, six-way total exactly100%, locks, visible exact values and explicit review/apply. **Coordinator-proposed editing algorithm:** changing an unlocked bar redistributes the remaining budget proportionally over the other unlocked bars; all-zero peers split equally; integer remainders use stable discipline order. Locked allocations never change during another edit. One unlocked bar cannot change; all locked is a legitimate read-only view. Unlocking alone never redistributes.

The existing [ScienceRules](../../../src/HobbyDS9.Simulation/ScienceRules.cs) and [ResearchUnits](../../../src/HobbyDS9.Contracts/ScienceEngineeringDtos.cs) require six integer weights summing **600**, not 10,000 basis points. This prototype preserves that precision, with one unit equal to⅙%. Exact fractional readouts avoid six rounded16.67% labels summing100.02%. Pointer, keyboard and precise-unit entry share the same local editor. Out-of-budget edits clamp only the edited unlocked share; no negative allocation or silent unlock is allowed.

Cancel changes explicitly restores accepted local weights; editor locks remain. Review cancel keeps the current draft. Apply confirms only the local fixture after reviewing all six values. No research is earned and no game command is sent. The Science/Engineering split retains a separate review link. Future native integration must use the existing stamped complete-six-way command and the independently reviewed split command. Visual references consulted: [LCARS slider conventions](../../lcars-ship-designer-sliders-v1.md) and [instrument-bank study](../../lcars-instrument-bank-v2-study.md); this is original CSS using the established amber/lavender/ice grammar, not borrowed imagery.

## Visual ship designer and compatible connections

Read against the owner's [modular ship art direction](E:/HobbyDS9/docs/art/modular-ships.md) and authoritative [ship-design chapter](../../design/ship-design.md). The hull stays fixed. The owned original cruiser raster provides the model focus; region controls and a close-up view focus forward equipment, nacelles or internal power. A schematic overlay distinguishes fitted baseline from selected replacement. Explicit preview fitting updates that local visual draft.

The owner's large-forward-deflector example is a **proposed typed/sized/located visual interface**, not a complete new socket catalogue. The forward sensor/large deflector examples share the declared forward Large interface; Small or Aft examples give incompatibility feedback and cannot be fitted. No arbitrary scaling/rotation makes them compatible. Standard anchor, scale, orientation and clearance apply only within a compatible interface class. Actual hull-family, capacity, mount, dependency and power validation remains required from existing data/compiler; visual compatibility never grants gameplay legality. Internal power uses a labelled schematic cutaway rather than invented exterior geometry. Exact catalogue/version-to-visual-socket mappings remain open.

Recommended Unity approach: **hybrid**, moving toward live assembled3D for designer/combat fit consistency. Prerendered views are cheap and predictable for initial hull browsing/close-ups, but every camera/module combination multiplies assets and cannot truthfully represent arbitrary fits. Runtime3D can reuse the same typed visual catalogue, highlight anchors and reflect installed versions, but needs authored meshes/interfaces, filtered fit data, resource ownership, LOD/material budgets, disposal and native input/performance acceptance. Hybrid uses owned thumbnails/backdrops while the selected valid assembly uses a bounded live camera when that scoped runtime work is accepted. This delivery only simulates appearance with a raster and schematic; no mesh is attached or claimed as native3D.
