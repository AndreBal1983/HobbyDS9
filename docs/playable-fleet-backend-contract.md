# Playable existing-class fleet backend — proposed format6 contract

20 October2026. Implementation assignment: owner-authorized existing-class paid construction, strategic fleet organization/Follow, interactive round playback and reports. This contract is committed before implementation for independent review. Source base e3e76216c5d1033ae51614e364ccb1717506bb99. No custom-design publication, refit, new classes/balance, client/GPU work, main merge or validated-pointer promotion.

## Actual gap and compatibility decision

Integrated3 already provides paid admitted-static-class construction and exact authored fit/provenance/stocks, queues, owned strategy/research, stamped known-route/Follow travel, simultaneous round commitments and atomic aftermath. Its ValidateBuiltShips deliberately requires current Ship.FleetId==BuiltShip.FleetIdAtConstruction. FleetStateDto/legacy14 has no display name. Travel saves prove the preceding movement and known fleet ownership. No create/transfer/name command exists.

A transient UI grouping cannot satisfy distinct authoritative tactical fleet identities or reload. A new command alone could change the current membership field, but the current integrated3 loader would reject the result. Weakening that check globally would admit substituted membership without a lawful operation history. Adding optional membership/name history fields under the same existing wrapper would introduce new authority that old serializers/loaders can silently discard. Therefore this bounded candidate adds an explicit wrapper6 with its own embedded-core marker and complete accepted-operation replay. Historical FleetIdAtConstruction remains immutable; current FleetId changes only through validated organization. Old1/2/3/4/5 loaders, fields, contracts and goldens retain their behavior. No implicit migration or fallback; truncated6 nested roots reject old loaders. Legacy Save14/Content11/rules science-engineering-v1/compiler ship-design-compiler-v1 unchanged.

## Fleet transaction policies

Only controlled-human Planning commands, exact turn/revision and stable unique command ID. Selected ships must be unique, existing, owned and at one node. Every source and existing destination must have no partial transit, no route and travel intent Stay; StayEngage/Follow/Leave accepted intentions must first be explicitly replaced through the existing travel API. Pending combat rejects organization. Create requires at least one ship and a trimmed nonblank name (maximum80 UTF-16 characters, no control characters); Transfer names no new fleet; Rename carries no ships and changes one owned fleet. Stable allocated fleet ID never derives from a name. Names may duplicate; IDs remain the identity.

Ship IDs, immutable hardware/provenance, hull, shields, ammunition, RNG and production records are unchanged. Empty source fleet entities/settings/orders are removed atomically; identities are never reused. Historical movement receipts and last-known contact records remain historical, including retired fleet identities, instead of retroactively erasing knowledge. A Follow of a now-absent contact cannot guarantee interception. Current receipts for surviving fleets retain their positions. Historical owner lookup for newly created/retired fleets is derived from accepted organization operations. Replay of complete history proves these exceptions; existing-profile validators remain strict.

No fleet/ship gameplay cap is introduced. Input selected-ship cardinality cannot exceed actual own roster. The new review package must explicitly declare its technical accepted-operation replay budget (accepted range 1–65536); no implicit4096 default. The supplied review fixture declares 2048. A local 2048-rename transcript (530693 serialized characters) reloaded in approximately one second; this measures a representative simple-operation case, not worst-case battle replay.

Before publishing an advance that admits combat, the complete staged batch must fit one advance slot, all remaining human round slots (4 minus each incomplete encounter's NextRound), and one batch-finalization slot. AI-only completed batches still reserve finalization. The single-human invariant makes every accepted combat command resolve exactly one round; nonprogress/stale/duplicate inputs cannot spend that reserve. Insufficient capacity rejects the entire advance before state, paid production, movement, IDs, AI resources or RNG publish. Exhaustion can stop Planning but cannot strand an accepted battle. Remaining capacity is a host diagnostic, not a gameplay statistic or victory condition. Raising the bound changes the explicit package identity, not a silent save migration. Completed battles are at most three rounds; playback projection is deterministic replay, never a mutation or new AI decision. Production and final history cost can grow with accepted operations; a long-running campaign requires a separately reviewed persistence design.

## Actor-safe playback and results

Stable identity is encounter+round+sequence. Only resolved rounds are returned. Existing per-fleet orders and current snapshots stay authoritative; skip/speed/camera state is presentation-only. Public events carry typed kind, lawful source/target ship/fleet, observable weapon visual class, sector/range and factual condition delta. No private opponent orders, hit probabilities, weapon IDs/reserve totals, hidden counts or hidden launcher identity/range. Round visibility is evaluated at that round's boundary; later reveal must not retrospectively identify an earlier hidden shot. Before/after boundaries expose own exact condition and only then-visible enemy condition. Maneuver geometry is projected from actual resolved geometry. Statistics are explicitly own or observed; damage totals are exact decimal integers to accommodate repeated shield damage beyond Int64, and mean damage received by that ship, not speculative attribution to an attacker. Shots/hits/misses are observed source events. Current pending save/reload preserves accepted-but-unresolved commands; loading replays only already-accepted operations and cannot decide another human round. Completed result history is reconstructed from those operations and retained after explicit aftermath. New fleets start with approach cloak disabled; existing destination settings persist. Ship stocks and equipment never reset.

## Capacity correction after independent review

The unreviewed implementation candidate 68ad1db could exhaust its history capacity during combat. The follow-up admission rule fixes that defect without changing old profiles, balance, numeric budget or save layout. Normal reviewed-path saves replay identically. A hypothetical unsafe pending save made by 68ad1db that did not reserve completion capacity now fails closed during accepted-operation replay; there is no migration, checkpoint import or unsafe continuation fallback. This unreviewed candidate is not a supported released-save contract.
