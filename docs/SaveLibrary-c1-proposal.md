Status: **proposed UI**, authorized scaffold, **not activated**. Baseline `2fc0dbca46073121379dd9491c859a02a6f22dcd` (outer save Format18/package5). Direction: reviewed ADR `docs/design/state-repository-savegame-adr.md` at `55a0c67`; implementation authorization `docs/design/state-repository-implementation-authorization-20261122.md` at `0fb1405`. ## Review surface

[Standalone 1920-layout mockup](mockups/SaveLibrary-c1-proposal.html). Illustration only: every name, turn, date and outcome in that mockup is fixture data. The runtime widget requires explicit supplied metadata and callbacks, has no default fixture and is not constructed anywhere in production.

Dark LCARS cells follow the Engineering language: amber navigation/primary controls, lavender section edges, navy cells, readable numeric columns. At 1920×1080 the left two-thirds holds a compact table; the right third holds the selected save, branch context and actions. The top status strip distinguishes current in-memory progress from last acknowledged durable progress. The widget keeps session status/warnings above a scrollable workspace, so dense details and recovery remain reachable. Long Unicode names wrap and render literally (rich text is disabled); duplicate display names remain distinct stable targets. Smaller windows use wrapping controls and scrolling as best effort, without a new minimum-size policy.

The table requests metadata pages of at most 50 rows. Case-sensitive Unicode name search, kind, health and creation-branch scope emit a new query with no cursor. Previous/Next pass opaque host cursors unchanged. The host supplies newest-first stable ordering and applies queries to the entire catalogue; this widget neither sorts a partial page into a misleading global result nor opens checkpoint payloads. The page caption need not contain a total: "25 shown · more available" is sufficient. The incoming Data cursor uses UpdatedUtc plus ID and a catalogue-sequence fence; catalogue changes require an explicit Conflict/restart, never guessed counts or bulk payload decoding. One outstanding metadata query freezes old controls until the host publishes a response or explicit error page using that request's boundary. A page status explains loading, empty or metadata error independently from save outcomes. Manual, Auto and Milestone are distinct; Quick Save is deferred.

Selecting a row shows its campaign, **creation branch**, saved-time caption, health and supplied turn. Creation branch is not reference membership or proof that the save belongs to current active history. The scope control says "Created on active branch". Metadata listing is not payload validation: an unchecked row offers **Check save**, issuing one exact-target `Validate` intent. Only a host-supplied validated result enables Load; host-supplied Checking stays non-loadable. The adapter must perform a bounded read and exact edition/Backend validation on demand, and revalidate before restore. Older-history rows explain that continuation branches on accepted mutation or explicit branch; later history remains. Corrupt/unchecked/incompatible/expired rows cannot issue Load. Rename, duplicate, overwrite and delete open an explicit target review. Confirmation captures reference ID, checkpoint ID, branch ID and expected reference/head generations; a stale target requires a fresh review. Export is an independent intent.

An always-present **Name for new save / Save current game…** control works even when the library is empty. `CreateManual` reviews the Unicode name, active branch, current progress and last confirmed save before emitting an intent. It generates no checkpoint, operation ID, receipt or capture, and never reuses a previous durable operation ID. The host must review/revalidate the actual later capture if admission waits. Blank names cannot proceed; Data remains authoritative for all actual naming bounds and repository rules.

## Durable state and recovery

The warning area remains present when autosave fails and the player chooses Continue singleplayer. Manual Save-and-Quit failure offers Return to session, retry of the **same existing operation**, export, and an explicit Quit without saving confirmation; emitting an intent never closes the session. Product headings are **Waiting to save**, **Saving**, **Saved**, **Save failed**, and **Save status needs checking**. Unknown does not become failure: Check save status requests receipt lookup; only an explicit host `OutcomeLookupInProgress` changes the heading to **Checking save status…**. No new operation IDs or receipts are created by this presentation.

Waiting is cancellable only with an explicitly supplied opaque **PendingRequestId**. `CancelWaitingRequest` carries that admission identity and no durable operation ID; it is unavailable after admission or without a pending identity. It cannot cancel a commit or erase a successful save. Current turn, last confirmed saved turn/time and unsaved state are normal product information. Raw revisions, IDs, generations and operation enum values are confined to a closed **Diagnostics** disclosure; supplied loss-window/detail text must also use suitable product wording. Last-saved time is supplied explicitly, never inferred from catalogue update time or a selected checkpoint; missing time is "Time not reported".

Recovery separately shows the newest damaged checkpoint and a host-validated candidate. The host supplies an explicit loss-window statement (including uncertain limits where applicable); turn subtraction across branches is not used. Review recovery requires confirmation of that exact candidate and loss window; no automatic fallback occurs. Even metadata marked validated must be checked again on load. No candidate or missing loss window means no recovery action.

Accepted policy summary is visible but not enforced by this scaffold: 10 rolling autosaves plus 3 milestones; 512 MiB **soft automatic-data budget**; manual saves protected; older continuations branch; Quick Save deferred. This is not a claim about physical database size, reclamation or implemented retention.

## Ownership and callback contract

`SaveLibraryPresentation.cs` contains immutable presentation data and a callback-boundary guard, not repository API types. Stable IDs, generations, source epoch and opaque cursors are supplied by the future adapter. Each rendered callback captures an epoch, catalogue generation and local render token, bound to that presentation instance. Republish/rerender invalidates detached controls; disposal/detachment retires the panel. An external `sourceIsCurrent` predicate also checks the caller's session ownership. Publishing a response requires the original live boundary, same epoch and nondecreasing generation. Even a replacement panel with matching epoch/generations rejects another panel's boundary. New sessions construct a new panel. Confirmation never silently rebases expected generations or resolves by display name.

The host must validate every intent against its actual source epoch, expected reference/head generations, operation receipt/fingerprint and policy. A callback being accepted locally does not establish a commit or validation result. The C1 panel cannot mutate the repository, select replacement-session state, retry, load, quit, delete files or operate on owner saves.

Row `BranchId`/caption map to the checkpoint's creation branch. Row `BranchGeneration` is nullable: Data metadata does not supply a creation-branch generation, so it remains unknown unless separately observed; never substitute zero. Reference generation remains required for reference CAS. Required `ActiveBranchGeneration` is separately supplied for current-state admission/overwrite. Confirmation comparisons preserve null as unknown, and neither creation metadata nor a reference name is treated as membership in current continuation history.

## Pending integration and checks

Pending: Data's exact DTO/receipt/query API mapping; metadata health/compatibility projection; durable stamp and recovery-loss wording; runtime host admission/retention/quiescence; filesystem export/recovery flows; production navigation/feature gate; native provider acceptance. Storage settings is not invented here; it stays a later host flow. Data naming validation remains authoritative; this scaffold does not turn proposed ADR name bounds into rules.

Portable tests exercise copied metadata, Unicode duplicate identities, opaque pagination, stale render/epoch/generation boundaries, explicit confirmation target checks, unknown outcome policy and recovery gating. Unity tests inspect the actual disconnected widget and its displayed controls; source/reference compilation is possible without starting Unity. **Native/visual/input QA is pending and belongs exclusively to QA**, including 1920 layout, hundreds of catalogue rows across pages, long Unicode names, keyboard focus, scroll, persistent warnings and recovery/manual-quit sequences. No tests here execute saves or a provider. Receiving must exclude the Unity-only `SaveLibraryPanel.cs` from the portable adapter wildcard; shared compiler configuration is outside this delta.

Initial validation on 22 November: **13 portable cases passed**, with both runtime sources and **5 widget fixtures** source-compiled. The overnight C1 follow-up expands this to **22 portable cases passed** and both actual runtime sources plus **10 widget fixtures** compiled against installed Unity6000.6.9f1 Managed and Unity-custom NUnit references with **0 errors, 0 warnings**. New checks cover empty-library named save review, withheld creation during unresolved writes, exact-target on-demand validation, host-only Checking/Validated transitions, separate pending-request cancellation, stale new controls, nullable creation-branch generations and product/diagnostic separation. The widget fixtures were **compiled only**, not executed. Ignored local check projects are under `artifacts/c1-check/portable` (.NET10) and `artifacts/c1-check/unity` (netstandard2.1); no shared compiler configuration or provider package was changed. This evidence does not establish Unity asmdef resolution, rendering, focus, native SQLite availability or save behavior.
